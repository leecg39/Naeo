# 관리자 목록의 100개 이후 접근 복구

2026-10-15 · 전체 페이지 CRUD 점검 중 문서·FAQ·공지 관리자가 pageSize=100 첫 페이지에 고정되어 다음 항목을 열 수 없는 문제를 확인했다. 원본 관리자 UI 역공학 결과가 아니라 클론 자체의 기능 결함이다.

## 변경

- 세 목록에 이전·다음 버튼과 현재/전체 페이지 표시를 추가했다. 처음·끝·처리 중에는 해당 버튼을 비활성화한다.
- API의 기존 page/pageSize를 전달한다. 검색 조건은 검색 버튼을 누를 때 적용하며 1페이지부터 조회한다. 아직 제출하지 않은 필터 입력은 페이지 이동에 섞이지 않는다.
- 생성 뒤에는 1페이지, 수정·삭제 뒤에는 현재 페이지를 갱신한다. 현재 페이지가 삭제로 사라졌으면 새 total에 따른 마지막 유효 페이지를 한 번 더 조회한다.
- 조회 실패는 기존 run/error 처리로 전달되고 성공한 결과만 목록에 반영한다. 권한·Origin·버전 충돌·요청 제한은 그대로 유지한다.

## 검증

API 핸들러에 연결한 격리 DB를 도메인마다 준비해 각각 101개를 생성했다. 1페이지100개+2페이지1개가 중복 없이 조회되는지, 2페이지 항목의 수정·삭제, 마지막 항목 삭제 후 실제 화면이 사용하는 loadValidPage가 2→1로 재조회하는지 확인했다.

첫 테스트는 한 관리자 세션에서 세 도메인을 연속 대량 생성하여 429 제한에 걸렸다. 제품 제한을 변경하지 않고 도메인마다 별도 DB/계정으로 분리해 통과시켰다.

전체409개(root6+server403)·lint·typecheck·production build 통과. evidence/pagination-tests.log와 pagination-build.log에 기록했다. 이 테스트는 Request/Response 핸들러 검사이며 실제 브라우저 클릭·페이지 포커스·검색 입력 유지 검증은 아니다.

## 남은 범위

RewardsManager·EntriesReview는 아래 추가 수정으로 페이지 이동을 연결했다. 후속 검색에서 EventsManager·PlansCoupons·PaymentsRefunds와 참여 심사 이벤트 선택 목록에도 100개 제한이 발견되어 계속 수정해야 한다. 외부 공급자·AI·전 페이지 실제 브라우저 검증 및 전체 목표는 계속 미완료다.


## 리워드·선택된 이벤트의 참여 목록 추가 수정

- 리워드 목록에 페이지 이동과 적용된 검색/상태/종류 유지, 새 지급 후1페이지·회수 후 현재 유효 페이지 갱신을 연결했다. 페이지를 바꾸면 이전 회수 확인 상태를 해제한다.
- 선택된 이벤트의 참여 목록에 페이지 이동을 연결했다. 이벤트/상태 변경은1페이지부터 조회한다. 조회가 성공한 뒤 상태와 이벤트 URL을 반영해 오류 때 선택과 결과가 어긋나지 않게 했다.
- submitted 필터에서 마지막 참여를 승인해 페이지가 사라지면 새 마지막 페이지로 돌아간다.
- 새 검증2개: 리워드101건의 2페이지 회수 후 잔액/100건/1페이지, 회원101명의 참여 중 2페이지 승인 후15토큰/대기100건/1페이지/다른 이벤트0건을 실제 DB·도메인 서비스와 화면 공용 loadValidPage로 확인했다.
- 최초 참여 테스트는 서비스 함수의 slug 인자 위치를 잘못 전달해 실패했다. 실제 시그니처에 맞춘 뒤 통과했다. 제품 API는 변경하지 않았다.

전체411개(root6+server405)·lint/typecheck/build 통과. evidence/event-pagination-tests.log·event-pagination-build.log 참조. 새 테스트는 도메인/DB 기반이며 실제 브라우저 심사·회수 클릭 검증은 아니다.

추가 한계: `/admin/event`에서 이벤트 자체를 고르는 목록도 첫100개에 제한된다. 이번 변경은 선택된 이벤트 안의 참여 목록을 처리한 것이며 101번째 이벤트 선택 문제를 해결한 것은 아니다. 이벤트 목록·선택기와 결제/환불/쿠폰 목록을 후속 P11.4로 추적한다.
