# 관리자 목록의 100개 이후 접근 복구

2026-10-15 · 전체 페이지 CRUD 점검 중 문서·FAQ·공지 관리자가 pageSize=100 첫 페이지에 고정되어 다음 항목을 열 수 없는 문제를 확인했다. 원본 관리자 UI 역공학 결과가 아니라 클론 자체의 기능 결함이다.

## 변경

- 세 목록에 이전·다음 버튼과 현재/전체 페이지 표시를 추가했다. 처음·끝·처리 중에는 해당 버튼을 비활성화한다.
- API의 기존 page/pageSize를 전달한다. 검색 조건은 검색 버튼을 누를 때 적용하며 1페이지부터 조회한다. 아직 제출하지 않은 필터 입력은 페이지 이동에 섞이지 않는다.
- 생성 뒤에는 1페이지, 수정·삭제 뒤에는 현재 페이지를 갱신한다. 현재 페이지가 삭제로 사라졌으면 새 total에 따른 마지막 유효 페이지를 한 번 더 조회한다.
- 조회 실패는 기존 run/error 처리로 전달되고 성공한 결과만 목록에 반영한다. 권한·Origin·버전 충돌·요청 제한은 그대로 유지한다.

## 검증

API 핸들러에 연결한 격리 DB를 도메인마다 준비해 각각 101개를 생성했다. 1페이지100개+2페이지1개가 중복 없이 조회되는지, 2페이지 항목의 수정·삭제, 마지막 항목 삭제 후 실제 화면이 사용하는 loadValidPage가 2→1로 재조회하는지 확인했다.

첫 테스트는 한 관리자 세션에서 세 도메인을 연속 대량 생성하여 429 제한에 걸렸다. 제품 제한을 변경하지 않고 도메인마다 별도 DB/계정으로 분리해 통과시켰다.

전체409개(root6+server403)·lint·typecheck·production build 통과. evidence/pagination-tests.log와 pagination-build.log에 기록했다. 이 테스트는 Request/Response 핸들러 검사이며 실제 브라우저 클릭·페이지 포커스·검색 입력 유지 검증은 아니다.

## 남은 범위

RewardsManager·EntriesReview는 아래 추가 수정으로 페이지 이동을 연결했다. 후속 검색에서 EventsManager·PlansCoupons·PaymentsRefunds와 참여 심사 이벤트 선택 목록에도 100개 제한이 발견되어 계속 수정해야 한다. 외부 공급자·AI·전 페이지 실제 브라우저 검증 및 전체 목표는 계속 미완료다.


## 리워드·선택된 이벤트의 참여 목록 추가 수정

- 리워드 목록에 페이지 이동과 적용된 검색/상태/종류 유지, 새 지급 후1페이지·회수 후 현재 유효 페이지 갱신을 연결했다. 페이지를 바꾸면 이전 회수 확인 상태를 해제한다.
- 선택된 이벤트의 참여 목록에 페이지 이동을 연결했다. 이벤트/상태 변경은1페이지부터 조회한다. 조회가 성공한 뒤 상태와 이벤트 URL을 반영해 오류 때 선택과 결과가 어긋나지 않게 했다.
- submitted 필터에서 마지막 참여를 승인해 페이지가 사라지면 새 마지막 페이지로 돌아간다.
- 새 검증2개: 리워드101건의 2페이지 회수 후 잔액/100건/1페이지, 회원101명의 참여 중 2페이지 승인 후15토큰/대기100건/1페이지/다른 이벤트0건을 실제 DB·도메인 서비스와 화면 공용 loadValidPage로 확인했다.
- 최초 참여 테스트는 서비스 함수의 slug 인자 위치를 잘못 전달해 실패했다. 실제 시그니처에 맞춘 뒤 통과했다. 제품 API는 변경하지 않았다.

전체411개(root6+server405)·lint/typecheck/build 통과. evidence/event-pagination-tests.log·event-pagination-build.log 참조. 새 테스트는 도메인/DB 기반이며 실제 브라우저 심사·회수 클릭 검증은 아니다.

추가 한계: `/admin/event`에서 이벤트 자체를 고르는 목록도 첫100개에 제한된다. 이번 변경은 선택된 이벤트 안의 참여 목록을 처리한 것이며 101번째 이벤트 선택 문제를 해결한 것은 아니다. 이벤트 목록·선택기와 결제/환불/쿠폰 목록을 후속 P11.4로 추적한다.


## 이벤트 목록·선택기 추가 수정

- EventsManager에 적용된 검색 조건·이전/다음·생성 후 첫 페이지·삭제 후 마지막 유효 페이지 복귀를 연결했다.
- 관리자 이벤트 API에 acceptsEntries=true/false 필터를 추가했다. DB에서 COUNT와 목록 조회 전에 적용하며 시작시각·생성시각이 같을 때 ID로 안정 정렬한다.
- 참여 심사 이벤트 선택기는 검색과20개 단위 페이지 이동을 제공한다. 현재 선택이 검색 결과 페이지 밖이어도 별도 선택 옵션으로 유지한다.
- 서버는 명시적 slug를 첫100개 목록에서 찾지 않고 직접 조회한다. 없는 이벤트/참여를 받지 않는 이벤트는404로 처리하며 다른 이벤트로 조용히 대체하지 않는다. slug 생략 시 필터링된 첫 이벤트를 사용한다.

검증: 가능101+불가101 이벤트를 생성해 6페이지의101번째 가능 이벤트 조회·제목 검색·권한·잘못된 필터 거부·수정/삭제 후 페이지 복귀를 검사했다. 전체412개(root6+server406), lint/typecheck/build 통과.

`node --import tsx scripts/qa/event-selector.ts`는 격리 production Next 서버에서 실제 HTTP로 필터/API 페이지6, 명시한101번째 이벤트의 심사 SSR, 없는/참여불가 slug가 다른 이벤트로 대체되지 않는 것을 확인했다. 임시 DB·프로세스 정리. evidence/event-selector-runtime.json 참조. 실제 브라우저 검색·select·페이지 버튼 클릭은 미검증이다.

남은 P11.4 범위는 쿠폰·결제·환불 목록이다. 앞선 발견 기록의 이벤트 목록/선택기 제한은 이번 수정으로 해소했지만 전체 사이트 완료를 뜻하지 않는다.


## 쿠폰·결제·환불 관리자 목록 (2026-10-15)

첫100건만 보이던 세 목록에 각각 페이지 이동을 연결했다. 쿠폰 생성 후 첫 페이지, 상태 변경 후 현재 페이지를 조회한다. 결제 검색은 입력 중인 값과 적용한 값을 분리하고 검색 시 결제 목록만 첫 페이지로 이동한다. 환불 목록 페이지는 독립적으로 유지한다. 환불 결정·결제사 조회 이후 두 목록을 각자의 현재 페이지에서 새로 읽으며, 마지막 페이지가 없어지면 유효한 마지막 페이지로 복귀한다. 같은 created_at 값에서 페이지가 흔들리지 않도록 ID 정렬 기준도 추가했다.

검증: 전체414개(root6+server408), lint/typecheck/build 통과. 도메인 테스트에서 같은 시각101개 쿠폰과101개 결제·환불의 중복 없는 페이지 분할, 두 번째 페이지 수정·거절, 상태 필터 복귀, 검색·권한·버전 충돌을 확인했다. 최초 테스트는 준비용 주문 삭제가 회계 기록 삭제 금지에 걸려 실패했다. 제품 제약은 유지하고 fixture에서 요금제를 직접 참조하도록 고쳤다.

`scripts/qa/billing-pagination.ts`는 격리한 DB와 실제 production Next 서버에서 각101건의 API 페이지 조회, 쿠폰 변경/409 충돌, 환불 거절, 결제 검색, 비인증401, 세 페이지 이동 컨트롤의 SSR을 검증했다. 외부 결제사는 호출하지 않았고 서버·임시 DB를 정리했다. [HTTP/SSR 기록](evidence/billing-pagination-runtime.json), [전체 테스트](evidence/billing-pagination-tests.log), [빌드](evidence/billing-pagination-build.log).

실제 브라우저 클릭·hydration·포커스·모바일 동작은 아직 확인하지 못했다(P11.3). 회원 자신의 결제·환불 조회에도 LIMIT50이 있어 별도 P11.5로 남겼다. 이 변경은 원본 Payple 결제 서버를 복원했다는 의미가 아니며 기존 로컬 결제 설계의 목록 접근 보완이다.

## 회원 결제·환불 전체 이력 (2026-10-15)

회원 설정과 `/api/billing/me`의 최신50건 제한을 해소했다. paymentsPage와 refundsPage를 독립 입력으로 받아 각50건, 총건수와 현재 페이지를 반환한다. 범위를 넘는 페이지는 마지막 페이지로 보정하고, 1 미만·정수 아님·100000 초과는400으로 거절한다. 기존 payments/refunds 배열은 유지하며 페이지 메타데이터를 추가했다. SSR과 API는 billingHistory 서비스를 공유한다.

설정에 결제·환불 각각 이전/다음 이동을 연결했다. 환불 표에는 주문명·번호, 금액·사유·상태·결정 메모·요청일을 표시한다. 결제 행의 상태는 해당 주문의 진행 중/최근 환불을 별도로 읽으므로 다른 환불 이력 페이지를 보더라도 진행 중 상태가 사라지지 않는다. 계정 ID는 인증된 서버 인수로만 결정한다.

전체415(root6+server409), lint/typecheck/build 통과. API 테스트는 반대 순서의51개 결제·환불을 만들어 중복 없는 전체 접근, 주문 연결, 페이지 독립성, 관련 환불 유지, 다른 계정 userId 매개변수 무효화, 회원 격리, 비인증401, 잘못된 입력400과 초과 페이지 보정을 확인했다.

실제 production Next 서버에서는101건으로3페이지의101번째 결제·환불, 주문별 환불 상태와 설정 SSR의 두 페이지 이동 컨트롤을 확인했다. 외부 결제사를 호출하지 않았고 임시 서버·DB를 정리했다. [HTTP/SSR](evidence/member-history-runtime.json), [테스트](evidence/member-history-tests.log), [빌드](evidence/member-history-build.log). 브라우저 hydration·클릭·모바일은 미검증이며 전체 사이트 완료 판정은 아니다.
