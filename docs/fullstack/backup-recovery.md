# 백업·복원 실패 복구 검증 — 2026-10-15

기존 구현에서 5개 테스트가 실패했다. 업로드 변경·누락을 검출하지 않았고, 업로드만 있는 대상도 force 없이 이동했으며, 마이그레이션 오류가 나기 전에 현재 자료를 이동했다. 같은 시각의 보존 사본도 덮어쓸 수 있었다. [RED 기록](evidence/backup-red.txt).

## 변경한 동작

- 형식 2 manifest에 DB 해시와 업로드별 상대 경로·크기·SHA-256을 저장한다. 누락·추가·손상을 검사하고 DB 무결성·외래키·마이그레이션 체크섬·테이블 건수도 확인한다. 원본 백업은 읽기 전용으로 열며 마이그레이션하지 않는다.
- 심볼릭 링크, 특별 파일, source/destination 겹침, DB/업로드 겹침, 기존 보존 사본과의 충돌을 거절한다. 시스템 별칭인 macOS `/var`는 실제 경로로 정규화한다.
- 대상 자료를 건드리기 전에 임시 사본의 검증과 마이그레이션을 완료한다. 업로드의 임시 위치는 업로드 대상과 같은 부모에 두어 DB와 업로드가 다른 볼륨에 있어도 볼륨 간 rename을 요구하지 않는다. 실제 별도 볼륨 환경은 이번 테스트에 포함하지 않았다.
- 복원 기록을 내구성 있게 게시한 뒤 기존 자료를 보존하고 새 자료를 설치한다. 양쪽 설치 후 커밋 상태를 기록한다. 파일 및 디렉터리에 fsync를 적용한다.
- 처리 가능한 오류는 자동으로 원래 상태로 복구한다. 강제 종료로 기록이 남으면 DB를 새로 열지 못하게 하고 `restore --offline --recover`를 요구한다. 커밋 전 기록은 롤백, 커밋 후 기록은 정리만 수행한다. 복구에 필요한 원래 사본이 없거나 해시가 달라졌으면 기록을 남긴 채 중단한다.

## 실제 검증

최종 전체 검사: `npm test` **339개(스크립트 6 + 서버 333)**, lint·typecheck·프로덕션 build 통과. 명령·소스 해시는 [검증 색인](evidence/backup-verification.json), 전체 로그는 같은 evidence 폴더에 있다.

[전용 검사](../../tests/server/backup.test.ts) 17개, [통과 기록](evidence/backup-green.txt):

1. 정상 백업 생성·검증·복원, 백업 이후 생긴 계정 제거, 이전 자료 보존.
2. 업로드 변경·누락·추가, 잘못된 manifest·구형 형식·추가 루트 파일 거절.
3. 심볼릭 링크·겹치는 경로·업로드만 있는 대상·기존 보존 사본 충돌 거절.
4. DB 해시를 다시 계산해도 외래키 위반·건수 불일치·비 SQLite 파일·마이그레이션 기록 오류 거절.
5. 원본 백업은 유효하나 새 마이그레이션이 실패하는 경우 현재 DB·업로드 유지.
6. DB 설치 후 업로드 설치 오류를 주입하고 기존 자료의 바이트가 보존되는지 검사. 원래 대상이 없던 경우에는 부분 설치를 제거.
7. 실제 별도 Node 프로세스를 DB 설치 직후 SIGKILL. 새 DB 연결 거절 확인 후 실제 CLI로 복구하고 두 계정·업로드 원본 바이트를 검증.
8. 실행 중인 PID가 기록된 경우 복구 거절. 복구 경로 변조·보존 사본 손상도 거절하고 기록을 유지.
9. 실제 두 파일 설치 이후 프로세스를 종료하고 커밋 마커가 있는 상태를 구성하여, 커밋된 자료를 유지하는 정리 분기를 검증. 이 마커는 테스트가 구성한 상태이며 실제 커밋 시점의 전원 차단 실험은 아니다.
10. 실제 백업 CLI가 offline 확인 없이 DB를 만들지 않는지, 원본 DB가 없으면 빈 DB를 생성하지 않고 실패하는지, offline 백업과 새 대상 복원 CLI가 성공하는지 확인.
11. 파일 수 0인 구형 백업의 DB 검증·복원·원본 manifest 보존. 실제 파일이 있는데 0이라고 선언하면 거절.
12. WAL 모드 DB를 검사해도 원본 폴더에 WAL/SHM이 생기지 않는지 반복 확인. readOnly 옵션에 더해 SQLite immutable 연결로 검사한다.

기존 로컬 QA 백업(`2026-10-13T19-57-40Z`, schema 25, 업로드 0개)의 임시 복사본도 확인했다. DB 체크섬은 일치했지만 profiles/sessions/audit_logs/consent_history/notification_preferences에서 users 외래키 위반이 각각 1건 발견돼 자동 복원을 거절했다. 원본 DB·폴더는 바꾸지 않았다. 이는 해당 과거 QA 자료의 판정이며 모든 구형 백업이나 현재 운영 DB에 대한 판정이 아니다. ## 운영 조건과 남은 범위

백업·복원 동안 웹 서버·작업자와 다른 기록기를 모두 멈춰야 한다. `--offline`은 확인 옵션이며 기록기 중단을 자동으로 탐지·강제하지 않는다. 기존에 열린 DB 연결을 강제로 종료하는 기능도 아니다. 업로드 복사 전후 체크섬 비교는 보조 검출이며 DB와 파일의 온라인 원자 스냅샷을 제공하지 않는다.

프로세스 강제 종료와 오류 주입은 검증했지만 호스트 전원 차단·디스크 하드웨어 오류·운영자가 동시에 파일을 변경하는 상황은 검증하지 않았다. 복구 기록과 보존 사본이 손상되면 자동 복구를 완료했다고 보고하지 않는다. 업로드가 있는 구형 백업은 원래 파일 체크섬이 없어 자동 복원을 거절한다. 백업은 암호화되거나 서명된 형식이 아니며 접근 제한과 보관 정책을 별도로 적용해야 한다.

이번 작업은 P9.2의 백업·복원 부분이다. 개인정보 내보내기와 기존 외부 연동·브라우저 검증은 미완료이며 전체 목표를 완료 처리하지 않는다. 실행 명령은 [운영 문서](operations.md)를 따른다.
