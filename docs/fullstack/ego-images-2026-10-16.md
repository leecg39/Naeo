# Ego 사진함 검증 — 2026-10-16

별도 임시 DB·업로드 폴더·localhost 프로덕션 서버를 사용했다. 기존 TaskSpace 0 / p1을 사용했다.

- 서비스 함수로 정상 PNG 101장을 준비했다. UI에서 로그인하고 다음 페이지를 클릭했다. photo-100.png의 complete 및 naturalWidth > 0을 확인했다.
- 삭제 버튼과 확인 대화상자를 실제 조작해 100장·1/1페이지 복귀를 확인했다. 포커스 BODY 손실을 재현했다.
- ImagePages의 안내에 OperationNotice를 적용했다. 공개 화면 스타일을 보존하도록 OperationNotice의 className/style을 선택적으로 받게 했다. 기존 관리자 기본 스타일은 유지했다.
- 새 빌드에서 실제 파일 입력으로 업로드해 101장으로 증가함을 확인했다. 데스크톱 클릭으로 마지막 사진 삭제 후 100장·1/1페이지·성공 안내 포커스를 확인했다.
- 390px에서는 실제 파일 입력 및 Enter 키로 동일 흐름을 확인했다. 모바일 포인터 검증은 아니다.
- 빌드 및 린트 통과. 전체 테스트는 재실행하지 않았다.
- 임시 서버·DB·업로드 파일·자격증명을 정리하고 원래 3000 포트 사진함으로 돌아왔다.

## 검증 중 발견했던 미완료 요구

캡처 화면에는 “마크다운을 복사해 AI 채팅에 붙여넣으면 … 자동 1600px 최적화” 안내가 남아 있다. ImagePages, uploadPhoto, 서버 media 구현을 확인한 범위에서는 사진함의 마크다운 복사 및 1600px 최적화 처리를 찾지 못했다. 단순 업로드·목록·삭제 통과를 원본 사진함 전체 기능 완료로 볼 수 없다. 원본 REA 근거와 확장 프로그램 전달 규약을 확인해 구현·검증해야 한다.

## 후속 해결

이 감사에서 발견한 누락은 이후 구현·검증했다. 업로드 이미지는 원본 최신 번들 계약에 맞춰 긴 변 1600px 이하 JPEG 0.85로 변환한다. 사진별·현재 페이지 전체 마크다운 복사, 독립 공개 링크 발행·철회·재발행, 사진 삭제 시 링크 폐기를 추가했다. Ego의 실제 운영체제 붙여넣기로 마크다운 문자열을 확인했고 공개 링크 200 → 철회 후 404 → 재복사한 새 토큰 200을 확인했다. 상세 근거는 [이미지 최적화](image-optimization-2026-10-16.md), [마크다운 링크](image-markdown-links-2026-10-16.md), [확장 전달 계약](extension-publish-extension.md)에 있다. 실제 네이버 편집기 전달은 P7.6 범위로 남긴다.
